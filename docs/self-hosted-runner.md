# Trusted Beta 1 Self-Hosted Runner

`v0.1.0-beta.1` requires one trusted Linux x64 runner for real local-model release validation. GitHub-hosted runners continue to execute every pull-request CI gate; the self-hosted runner is reserved for code already merged into the protected `develop` branch or for an explicit manual workflow dispatch.

## Why the runner is restricted

This repository is public. GitHub warns that persistent self-hosted runners can be compromised by untrusted pull-request code. Therefore:

- no self-hosted workflow is triggered by `pull_request`;
- release validation runs only on `push` to `develop` or `workflow_dispatch`;
- LangSmith evaluation is manual (`workflow_dispatch`);
- the runner must not contain unrelated personal credentials;
- Podman and the GitHub runner should run under a dedicated local account when practical.

## Reference machine

Minimum validated by `make doctor`:

- Linux x64;
- 8 logical CPU threads;
- 8 GiB RAM minimum;
- 8 GiB free disk minimum;
- rootless Podman;
- a Compose provider available through `podman compose`;
- Python 3.12 managed/resolved by `uv`;
- `uv`;
- Node.js 24 + npm;
- Git;
- local ports `4566`, `8080`, and `8081` available.

More RAM and disk are recommended because the runner keeps two local GGUF models and OCI image layers.

## Prepare rootless Podman

On Fedora, install Podman and a Compose provider if they are not already present:

```bash
sudo dnf install -y podman podman-compose
```

Enable the rootless Podman API socket and keep the user service available even without an interactive login:

```bash
systemctl --user enable --now podman.socket
sudo loginctl enable-linger "$USER"
```

The project defaults to the rootless socket:

```text
/run/user/<uid>/podman/podman.sock
```

Verify it before registering the runner:

```bash
podman --version
podman compose version
podman info
test -S /run/user/$(id -u)/podman/podman.sock
```

Floci runs against Podman's Docker-compatible API. The compose topology mounts the rootless Podman socket into Floci as `/var/run/docker.sock:z`, uses a named network, and forces the Lambda Runtime API host to `floci` for reliable rootless networking.

## Register the runner

1. Open the repository in GitHub.
2. Go to **Settings → Actions → Runners**.
3. Select **New self-hosted runner**.
4. Choose **Linux** and **x64**.
5. Run the download/extract commands GitHub generates on the target machine.
6. Use the repository URL and the one-hour registration token shown by GitHub. Add the custom label `rag-e2e` during initial configuration:

```bash
./config.sh \
  --url https://github.com/dfc-coder/rag-ops-guard \
  --token <GITHUB_GENERATED_REGISTRATION_TOKEN> \
  --name rag-e2e-local \
  --labels rag-e2e
```

The standard labels `self-hosted`, `linux`, and `x64` are added automatically by GitHub. The workflow requires all four labels:

```yaml
runs-on: [self-hosted, linux, x64, rag-e2e]
```

The registration token is intentionally not stored in this repository and expires after one hour.

## Validate the machine before enabling release jobs

From a normal checkout:

```bash
make doctor
```

Expected final line:

```text
doctor: PASS
```

Then verify the local runtime once manually:

```bash
make setup
make models
make local-up
make local-provision
make seed
make ingest-corpus
make smoke
make local-down
```

## Start the GitHub runner

Use the command generated by GitHub after configuration (`./run.sh`) or install the runner as a Linux service using GitHub's generated service instructions. The runner is ready when GitHub shows it as **Idle** under Settings → Actions → Runners.

## Persistent model cache

Model files are intentionally stored outside the GitHub checkout so `actions/checkout` with `clean: true` cannot delete several gigabytes of validated GGUF files between release jobs.

The default cache is:

```text
~/.cache/rag-ops-guard/models
```

Override it with `MODEL_DIR` when needed. `make models` reuses a model only after its pinned SHA256 matches. Interrupted downloads remain as `.part` files and resume with HTTP Range requests when the remote server supports them. Transient DNS/network failures are retried with bounded backoff. A checksum mismatch deletes the incomplete artifact and remains a release blocker.

The cache contains only public model artifacts. Do not store credentials or unrelated files there.

## Release behavior

When a trusted PR is squash-merged into `develop`, the `release-validation` workflow runs:

1. model checksum validation/download;
2. Floci + both llama.cpp servers under Podman;
3. local AWS-compatible provisioning;
4. corpus upload and ingestion;
5. real query E2E;
6. adversarial suite;
7. 30-case golden benchmark;
8. RAGAS thresholds;
9. clean-checkout reproducibility.

Only after `release/gate` and `ci/gate` are green should `develop` be promoted to `main` and tagged `v0.1.0-beta.1`.
